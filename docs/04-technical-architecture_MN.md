## 1. Зорилго ба архитектурын зарчмууд

### 1.1 Энэ архитектур юуг шийдэх вэ

HMS дамжлагын **зөвлөх систем (Phase 1, shadow mode)**-ийн программ хангамжийг хэрхэн барих вэ гэдгийг тодорхойлно. Үүнд: ямар сервер хэрэгтэй, PLC-тэй яаж холбогдох, өгөгдлийг хаана хадгалах, SP зөвлөмжийг ямар бүрэлдэхүүн хэсэг тооцоолох, оператор юутай харьцах вэ.

Хамрах хүрээ нь **Doc 01 §4 (BAГTAX ЗҮЙЛС)**-тэй яг тэнцүү. Энэ документ scope-ыг өргөтгөхгүй — зөвхөн түүнийг хэрхэн барихыг хэлнэ.

### 1.2 Долоон архитектурын зарчим

| # | Зарчим | Утга |
|---|--------|------|
| 1 | **Универсал цөм + үйлдвэрийн config** | Программын код нь аль ч DMC үйлдвэрт ажиллана. Үйлдвэр тус бүрийн ялгаатай зүйл (циклоны хэмжээ, PLC tag, хязгаар, тоног төхөөрөмж) бүгд **Doc 03 config файлд** байна. Шинэ үйлдвэрт = config хуулна, код өөрчлөхгүй. |
| 2 | **Shadow mode — зөвхөн унших** | Систем PLC руу хэзээ ч бичихгүй. Зөвхөн зөвлөнө, оператор шийднэ (Doc 01 §7). |
| 3 | **On-premise** | Сервер үйлдвэр дээрээ суух. Үүлэн хадгалалт байхгүй (Doc 01 §5 — өгөгдлийн өмчлөл, сүлжээний найдвар). |
| 4 | **Graceful degradation** | Манай систем уначихсан ч үйлдвэр хэвийн ажиллана. Бид нэмэлт давхарга — суурь биш. |
| 5 | **Энгийнээс эхэл, ухаалаг руу дараа** | Phase 1 = дүрэм + физик + энгийн статистик. Гүн ML байхгүй (Doc 01 §5). Архитектур нь дараа ML нэмэх боломжтой байдлаар бүтнэ. |
| 6 | **Бүгд бүртгэгдэнэ** | Зөвлөмж бүр, операторын шийдвэр бүр хадгалагдана — ирээдүйн ML загварын сургалтын өгөгдөл болно. |
| 7 | **Тохиргоо нь код биш, өгөгдөл** | Хязгаар, threshold, tag нэр — бүгд өгөгдлийн санд / config файлд. Программист дуудалгүйгээр инженер өөрчилж чадна. |

> **Энгийн үгээр.** Бид нэг үйлдвэрт зориулсан программ биш, **аль ч DMC үйлдвэрт тохирох программ** хийж байна. Тийм учраас "энэ үйлдвэрийн тоо" ба "программын логик" хоёрыг хатуу салгасан. Систем нь зөвхөн ажиглаж, зөвлөдөг — гар хүрдэггүй. Унавал үйлдвэр зогсохгүй.

## 3. Бүрэлдэхүүн хэсгүүд

### 3.1 Өгөгдөл цуглуулагч (Collector)

**Үүрэг:** PLC-аас процессын утгыг тогтмол уншиж өгөгдлийн санд бичих.

- **Протокол:** OPC UA-г түрүүлж сонгоно (орчин үеийн стандарт). Боломжгүй бол Modbus TCP, эсвэл одоо байгаа SCADA/historian-аас унших. Протокол нь **config дахь "driver" сонголт** — кодыг өөрчлөхгүйгээр сольж болно.
- **Уншилтын давтамж:** tag тус бүрт тохируулж болно (хурдан tag 1–5 сек, удаан tag 30–60 сек). Config-оос ирнэ.
- **Tag зураглал:** ямар PLC tag-ийг ямар хэмжигдэхүүн рүү буулгахыг **Doc 03 §10**-ийн tag жагсаалт тодорхойлно. Код дотор tag нэр хатуу бичигдэхгүй.
- **Эрүүл мэнд:** хоцролт (lag), алдагдсан tag, uptime-ыг хянана. Холболт тасарвал дахин холбогдох, алгасагдсан хугацааг тэмдэглэнэ.
- **Чиглэл:** зөвхөн READ. Бичих функц кодод **байхгүй** — алдаагаар ч бичих боломжгүй.

> **Энгийн үгээр.** Энэ бол DCS-ийн сканнер шиг — PLC-аас тоо хуулж авч хадгалдаг. Гэхдээ зөвхөн "хуулдаг", "буцааж бичдэг" функц нь огт байхгүй.

### 3.2 Гар оруулгын модуль (Manual Entry)

**Үүрэг:** PLC-д байдаггүй өгөгдлийг хүн оруулах вэб форм.

| Өгөгдөл | Хэн оруулна | Давтамж |
|---------|-------------|---------|
| Лабын тэжээл/бүтээгдэхүүний дээжний хариу (ash%, чийг, ширхэг) | Лаб / инженер | 2 цаг тутам авдаг дээж (хариу ~12 ц дараа) |
| Бүх циклийн дээжний хариу | Лаб / инженер | 12 цаг тутам |
| Washability үр дүн | Инженер | Нүүрс/seam бүрт нэг удаа |
| Тоног төхөөрөмжийн хэмжилт (spigot/vortex finder элэгдэл, running hours) | Засварын инженер | 7 хоног бүрийн зогсолтоор |
| Тэжээлийн blend бүрэлдэхүүн | Инженер | Blend өөрчлөгдөх бүрт |

- Оруулгад **шалгалт (validation)** хийнэ — утга боломжит хязгаарт байгаа эсэх, талбар дутуу эсэх.
- Бүх оруулга **хэн, хэзээ** оруулсныг бүртгэнэ.

> **Энгийн үгээр.** Лабын хариу, долоо хоногийн хэмжилт зэрэг "PLC мэддэггүй" зүйлийг энд гараар оруулна. Форм нь буруу тоо оруулахаас сэргийлж шалгана.

### 3.3 Өгөгдлийн сан (Database)

**Үүрэг:** бүх өгөгдлийг нэг дор, найдвартай хадгалах.

- **TimescaleDB** — PostgreSQL дээр суурилсан, цаг хугацааны цуваанд тусгайлсан өргөтгөл.
- PLC tag-ийн хурдан цуваа → **hypertable** (цаг хугацаагаар автоматаар хуваагдсан хүснэгт).
- Лаб, тоног төхөөрөмж, washability, кейс сан, зөвлөмж, шийдвэр, аудит лог → энгийн харьцаат хүснэгт.
- **6 сараас доошгүй** түүхэн өгөгдөл хадгална (Doc 01 §4.1).
- Өдөр бүр автомат нөөцлөлт (backup).

> **Энгийн үгээр.** Энэ бол үйлдвэрийн historian/data logger шиг — бүх тоо энд хадгалагдана. TimescaleDB нь олон сая мөр өгөгдлийг хурдан хадгалж, эргүүлж татаж чаддагаараа сонгогдсон.

### 3.4 Боловсруулах хөдөлгүүр (Processing Engine) — тархи

**Үүрэг:** өгөгдлийг харж, аюул шалгаж, аномал илрүүлж, SP зөвлөмж тооцоолох. Энэ бол **Doc 02-ийн домэйн логик кодлогдсон хэлбэр**.

Гурван түвшний логиктой — §4-д дэлгэрэнгүй. Энэ хөдөлгүүр:

- Шинэ өгөгдөл орох бүрт, эсвэл тогтсон хуваарьт ажиллана.
- Online proxy (Doc 02 §7) тооцоолно: нягт-vs-даралт, насосны хурдны drift, underflow/overflow тэнцвэр.
- Хоёр түвшний washability загвар (Doc 02 §5.2.1): теори = физик хүрээ, кейс сан = өмнөх угаалтын түүхтэй тулгах.
- Тоног төхөөрөмжийн элэгдэлд тааруулж залруулна (Doc 03 §17 — жишээ нь spigot элэгдвэл насосны хурд бага зэрэг нэмж даралт бариулна).
- Зөвлөмж бүр **тайлбартай** ("яагаад ийм утга вэ").

> **Энгийн үгээр.** Энэ бол системийн "баяжуулагч инженер тархи". Doc 02-д бичсэн бүх мэдлэгийг код болгож, өгөгдөл дээр ажиллуулж, зөвлөмж гаргадаг хэсэг. Phase 1-д энэ нь дүрэм + физик тооцоо — ид шидийн "хар хайрцаг" биш, тайлбарлаж болдог логик.

### 3.5 API давхарга (FastAPI)

**Үүрэг:** өгөгдлийн сан/хөдөлгүүр ба дэлгэцийн хооронд гүүр.

- REST endpoint-ууд: одоогийн утга, чиг хандлага, зөвлөмж, Accept/Reject/Modify, гар оруулга, KPI.
- Нэвтрэлт ба эрхийн 3 түвшин (§11).

> **Энгийн үгээр.** Дэлгэц "өгөгдөл өгөөч" гэж энэ давхаргаас гуйна. Аюулгүй хаалга — хэн юу үзэхийг энд шалгана.

### 3.6 Дэлгэцийн давхарга (Presentation)

**Үүрэг:** оператор/инженер/даргад өгөгдөл ба зөвлөмжийг харуулах.

| Хэсэг | Phase 1 шийдэл | Тайлбар |
|-------|----------------|---------|
| Real-time самбар, чиг хандлага, KPI | **Grafana** | Бэлэн хэрэгсэл — UI хөгжүүлэлт шаардахгүй, шууд ашиглаж эхэлнэ |
| SP зөвлөмжийн карт (Accept/Reject/Modify) | Хөнгөн вэб апп | Эхэндээ энгийн, дараа React (Phase 2) |
| Гар оруулгын форм | Хөнгөн вэб апп | §3.2 |
| Анхааруулгын урсгал | Grafana + вэб апп | |

- Phase 1 — **зөвхөн монгол хэл** (Doc 01 §5).
- Phase 1 — **зөвхөн вэб**, гар утасны апп байхгүй (Doc 01 §5).

> **Энгийн үгээр.** Эхлээд Grafana гэдэг бэлэн самбар хэрэгслийг ашиглаж график, KPI-г хурдан гаргана — энэ нь хэдэн долоо хоног хэмнэнэ. Зөвлөмжийн карт зэрэг тусгай дэлгэцийг л өөрсдөө хийнэ.

## 4. Боловсруулах хөдөлгүүр — гурван түвшний логик

Хөдөлгүүр гурван түвшинд ажиллана. Доод түвшин нь хамгийн яаралтай, дээд түвшин нь хамгийн "ухаалаг".

### 4.1 Tier 1 — Аюулгүй байдлын шалгалт

**Эх сурвалж:** Doc 02 §10 (гажиг нөхцөл, эмерженси).

Хатуу хязгаараас гарсан эсэхийг шалгана: нягтын runaway, насос choke, магнетитийн дутагдал, циклоны блокаж, феедийн алдагдал, цахилгаан тасрах, overflow flooding.

- Илрэхэд **шууд анхааруулга** өгнө.
- Систем зөвхөн **анхааруулна** — гар хүрэхгүй. PLC-ийн өөрийн аюулгүй байдлын логик хэвээрээ, бид түүнтэй огт оролцохгүй (Doc 01 §7.2).

### 4.2 Tier 2 — Аномал илрүүлэх

**Эх сурвалж:** Doc 01 §4.3 + Doc 02 §3.6, §6.

Дүрэмд суурилсан drift илрүүлэлт: нягт хязгаараас гарах, циклоны даралтын drift/огцом өөрчлөлт, feed flow vs SP тогтмол алдаа, лабын ash жишгээс гадуур, тоног төхөөрөмжийн running hours threshold давах → **сэлбэгийн сануулга**.

> Тэмдэглэл: энд зөвхөн running-hours threshold-д суурилсан **энгийн сануулга** орно. Чичиргээний анализ, урьдчилан таамаглах засвар (predictive maintenance) нь Phase 2 (Doc 01 §5).

### 4.3 Tier 3 — SP зөвлөмж

**Эх сурвалж:** Doc 02 §5 (washability → density логик), §5.2.1 (хоёр түвшний загвар), §7 (online proxy).

Систем **media density** ба **насосны хурд (pump speed SP)**-ыг хоёуланг нь зөвлөнө. *(VFD баталгаажсан — насосны хурд бодит, удирдаж болох SP хувьсагч.)*

**Оролтууд:**

- Одоогийн online proxy утгууд (нягт-vs-даралт, насосны хурдны drift, underflow/overflow тэнцвэр).
- Тэжээлийн "гарын үсэг" (feed signature): сүүлийн лабын ash, ширхэглэл, blend бүрэлдэхүүн.
- Washability өгөгдөл (тухайн нүүрс/seam-ийн).
- Долоо хоногийн тоног төхөөрөмжийн хэмжилт (элэгдэл).
- Өмнөх угаалтын түүх (кейс сан).

**Логик:**

1. **Tier 1 — Washability теори:** боломжит density-ийн **физик хүрээ/хязгаарыг** тогтооно. Хариулт энэ хүрээнээс гарахгүй.
2. **Tier 2 — Кейс сан:** одоогийн feed signature-ийг **өмнөх ижил төстэй угаалтуудтай** тулгаж, тэр үед амжилттай байсан density-г санал болгоно.
3. **Элэгдлийн залруулга:** spigot/vortex finder элэгдсэн бол насосны хурдыг залруулж даралт бариулна (Doc 03 §17).
4. Зөвлөмж бүрт **тайлбар** дагалдана.

**Зөвлөмж хэзээ гарах вэ:**

| Гох (trigger) | Жишээ |
|---------------|-------|
| Шинэ blend / feed чанар өөрчлөгдөх | Шинэ давхаргын нүүрс орж ирэх |
| Долоо хоногийн хэмжилт шинэ орох | Зогсолтын дараа элэгдлийн утга шинэчлэгдэх |
| Ээлжийн эхэнд | Шинэ оператор гарах |
| Оператор өөрөө хүсэх | "Зөвлөмж шинэчил" товч |

Online proxy-ийн тасралтгүй жижиг хазайлтыг Tier 2 анхааруулгаар зохицуулна.

**Бүх зөвлөмж + операторын хариу (Accept/Reject/Modify + шалтгаан) бүртгэгдэнэ** — Doc 01 §4.4.

> **Энгийн үгээр.** Tier 1 = "болохгүй зүйлийг хэзээ ч болиулахгүй" — гал унтраагч. Tier 2 = "ямар нэг юм хазайж байна" — дохио. Tier 3 = "ийм нягт, ийм хурд тавь" — зөвлөгөө. Tier 3 нь washability-аас хүрээ авч, түүхээс хариу авч, элэгдэлд тааруулна — яг таны §17-д тайлбарласан санаа.

## 5. Өгөгдлийн загвар (Data Model)

Өгөгдлийн санд байх үндсэн хүснэгтүүд:

| Хүснэгт | Төрөл | Агуулга |
|---------|-------|---------|
| `plc_readings` | Time-series (hypertable) | PLC tag бүрийн утга, цаг хугацаатай |
| `lab_results` | Харьцаат | Лабын дээжний хариу |
| `washability` | Харьцаат | Нүүрс/seam бүрийн washability муруй |
| `equipment` | Харьцаат | Тоног төхөөрөмжийн жагсаалт, running hours |
| `wear_measurements` | Харьцаат | Долоо хоногийн элэгдлийн хэмжилт |
| `case_library` | Харьцаат | Өмнөх угаалтын кейсүүд (Tier 2-ийн суурь) |
| `recommendations` | Харьцаат | Гарсан SP зөвлөмж + тайлбар |
| `decisions` | Харьцаат | Операторын Accept/Reject/Modify + шалтгаан |
| `alerts` | Харьцаат | Tier 1/2 анхааруулгууд |
| `audit_log` | Харьцаат | Хэн, юу, хэзээ |
| `users` | Харьцаат | Хэрэглэгч, эрхийн түвшин |
| `plant_config` | Харьцаат | Doc 03-ийн config (tag зураглал, хязгаар) |

**Чухал нарийн зүйл — лабын хоёр цаг.** `lab_results` хүснэгт нь хоёр өөр цагтай: **дээж авсан цаг** (`sample_time`) ба **хариу оруулсан цаг** (`entry_time`). Эдгээрийн зөрүү ~12 цаг. Хөдөлгүүр лабын утгыг **бодит цагийн SP-д биш**, өдөр тутмын калибровт ашиглана (Doc 01 Decision Log, 2026-05-18).

**Кейс сангийн бүтэц.** Кейс бүр: feed signature (ash, ширхэг, blend) + хэрэглэсэн density + хэрэглэсэн насосны хурд + үр дүн (yield, бүтээгдэхүүний ash) + тухайн үеийн тоног төхөөрөмжийн төлөв. Tier 3 одоогийн нөхцөлийг эдгээр кейстэй тулгана.

> **Энгийн үгээр.** Бүх өгөгдөл хүснэгтэд эмх цэгцтэй хадгалагдана. Лабын хариу 12 цаг хоцордог тул "хэзээ дээж авсан" ба "хэзээ хариу ирсэн" хоёрыг тусад нь бичнэ — эс тэгвэл систем хуучин хариуг "одоогийнх" гэж андуурна.

## 6. Өгөгдлийн урсгал — бодит жишээ

**Жишээ: циклоны даралт аажмаар буурч байна.**

1. Collector primary циклоны даралтыг 2 сек тутам уншиж `plc_readings`-д бичнэ.
2. Боловсруулах хөдөлгүүр сүүлийн 30 минутын даралтыг хараад **аажмаар буурах хандлага** илрүүлнэ (Tier 2).
3. Хөдөлгүүр online proxy-г тооцно: нягт тогтвортой, насосны хурд тогтвортой → даралт буурсан нь **spigot элэгдсэний** дохио (Doc 02 §3.6).
4. Tier 2 анхааруулга үүснэ: *"Primary циклоны даралт 30 мин дотор 8% буурсан. Нягт/хурд тогтвортой тул spigot элэгдэл сэжиглэж байна. Долоо хоногийн хэмжилтээр шалгана уу."*
5. Хөдөлгүүр Tier 3-д шилжинэ: даралт бариулахын тулд **насосны хурдыг +X rpm нэмэх** зөвлөмж гаргана (физик хүрээнд багтаан).
6. Зөвлөмж API-аар дамжиж операторын дэлгэцэнд карт болж гарна — тайлбартай.
7. Оператор Accept/Reject/Modify дарна. Сонголт `decisions`-д, бүх үйлдэл `audit_log`-д бичигдэнэ.

> **Энгийн үгээр.** Тоо орж ирэх → систем "энэ юу вэ" гэж бодох → оператор луу зөвлөмж очих → оператор шийдэх → шийдвэр бүртгэгдэх. Систем хэзээ ч өөрөө хурд өөрчлөхгүй.

## 7. Түүхэн өгөгдөл импортлох зам

Та одоо **бодит түүхэн өгөгдөлтэй** (PLC экспорт + лабын хариу). Энэ нь архитектурт нэг чухал бүрэлдэхүүн нэмнэ:

**Backfill хэрэгсэл (нэг удаагийн импорт).**

- PLC экспортын файл (CSV г.м.) ба лабын хариуг `plc_readings` / `lab_results`-д буулгана.
- Түүхэн угаалтуудаас **кейс сан үүсгэнэ** — Tier 2 эхнээсээ хоосон биш, бодит кейстэй эхэлнэ.
- Боловсруулах хөдөлгүүрийг **бодит өгөгдөл дээр** барьж, шалгаж болно — PLC-тэй амьд холболт хийхээс өмнө.

**Яагаад чухал вэ.** Ихэвчлэн ийм системийг synthetic (хиймэл) өгөгдөл дээр л барьдаг. Танд бодит дата байгаа тул:

- Зөвлөмжийн логикийг бодит угаалтын үр дүнтэй тулгаж **батлах** боломжтой.
- Самбар, чиг хандлагыг бодит дата дээр харуулна — хиймэл биш.
- Pilot эхлэхээс өмнө "энэ зөвлөмж зөв байсан уу" гэдгийг түүх дээр буцааж шалгана (backtesting).

> **Энгийн үгээр.** Танд бодит дата байгаа нь том давуу тал. Систем барих явцад "хиймэл тоо"-ны оронд жинхэнэ үйлдвэрийн түүхийг ашиглана. Зөвлөмжийг "өнгөрсөнд хэрэв ингэж зөвлөсөн бол зөв байх байсан уу" гэж шалгаж болно.

## 9. Байршуулалт ба сүлжээний топологи

### 9.1 Сүлжээний топологи

```
  ҮЙЛДВЭРИЙН PLC СҮЛЖЭЭ            ТУСГААРЛАГДСАН VLAN
  ┌────────────────────┐         ┌──────────────────────────┐
  │  PLC / SCADA        │         │  App сервер (on-premise)  │
  │                     │  read-  │  · Collector              │
  │  OPC UA сервер ─────┼────────►│  · TimescaleDB            │
  │  (read-only данс)   │  only   │  · Processing engine      │
  │                     │ ◄══╳══  │  · FastAPI · Grafana      │
  └────────────────────┘  бичих  └────────────┬─────────────┘
                          хориотой              │
                                                │ HTTP
                                   ┌────────────┴─────────────┐
                                   │  Операторын ажлын станц   │
                                   │  (вэб хөтөч)              │
                                   └──────────────────────────┘
```

- App сервер нь **тусгаарлагдсан VLAN**-д суух (Doc 01 §7.5).
- PLC сүлжээ рүү зөвхөн **нэг чигийн уншилт** — read-only OPC UA данс + firewall дүрэм нэг л холболт зөвшөөрнө.
- Хамгийн өндөр баталгаа: тоног төхөөрөмжийн **data diode** (нэг чигийн хаалга) — Phase 2-ийн сонголт, Phase 1-д шаардлагагүй.

### 9.2 Серверийн санал болгох үзүүлэлт

Нэг HMS дамжлага, ~20–40 tag, 1 сек уншилт — энэ нь хүнд ачаалал биш:

| Нөөц | Доод | Санал |
|------|------|-------|
| CPU | 4 цөм | 8 цөм |
| RAM | 16 GB | 32 GB |
| Диск | 500 GB SSD | 1–2 TB SSD |
| ОС | Ubuntu Linux эсвэл Windows Server | Ubuntu Linux |

> **Энгийн үгээр.** Сервер нь үйлдвэрийн өөрийн сүлжээнээс **тусдаа** суух — PLC рүү зөвхөн "сонсох" холболттой, "ярих" холболтгүй. Энэ нь манай систем хэзээ ч PLC-д нөлөөлөхгүй гэдгийн **физик баталгаа**. Шаардагдах сервер нь даруухан — энгийн нэг сервер хангалттай.
